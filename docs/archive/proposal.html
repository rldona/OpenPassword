Proposal v0.1 · 29 Oct 2026 · Android first

OpenPassword

An open-source, serverless password, card, PIN and secret manager. Everything is encrypted on the phone before it touches the disk. The app has no Internet permission: the backup leaves encrypted and the user decides where to store it.

1 · Principles

Five rules that override any feature

Zero knowledge

Nobody except the user can decrypt the vault: not us, not Google, not the provider where the backup lives.

Offline by design

The main build does not declare INTERNET. If it cannot connect, it cannot leak anything, and anyone can verify it in the manifest.

Everything encrypted, metadata too

Titles, URLs, categories and dates of each item are encrypted. On disk there are only identifiers and opaque blobs.

Boring cryptography

Standard primitives and audited libraries. Nothing invented. A single cryptographic core for all platforms.

Auditable and reproducible

Open source, reproducible builds, distribution through F-Droid and GitHub, a documented file format and an external audit before 1.0.

MVP features

  • Guided setup: master password, secret key generation and emergency kit.
  • Unlock with master password or strong biometrics (class 3).
  • List with instant search, categories, favourites and tags.
  • Detail view with reveal, copy and automatic clipboard wipe after 30 s.
  • Generator of random passwords, passphrases (EFF list in Spanish and English) and PINs.
  • Auto-lock by time, when the screen turns off and when the app goes to the background.
  • Export and import encrypted backup (.opvault).

After the MVP

  • v1 Android autofill service and built-in TOTP.
  • v1 Automatic backup to a folder chosen by the user.
  • v1 Offline vault health: weak, reused and old passwords; cards about to expire.
  • v1 Import from Bitwarden, KeePass (KDBX), 1Password (1PUX) and CSV.
  • v2 Multiple vaults (personal, family) and sync between devices.
  • v2 Passkeys and attachments.

Key hierarchy

Inspired by 1Password's two-secret derivation. The master password never encrypts data directly: it only unlocks the vault key, so it can be changed without re-encrypting everything.

  • Secret key (SK): 128 random bits generated during setup. It lives on the device (protected by Keystore) and in the paper emergency kit.
  • KEK: derived from the master password with Argon2id and mixed with the SK through HKDF. It is never stored.
  • Vault key (VK): 256 random bits. It is stored wrapped by the KEK and, if biometrics are enabled, also by a Keystore key.
  • Per-item key (IK): each item has its own, wrapped by the VK. It makes sharing items easier in the future and limits the damage of a flaw.

Android hardening

  • No INTERNET permission in the main build. It is verified in CI.
  • allowBackup="false" and empty extraction rules: Google does not back up the vault.
  • FLAG_SECURE on every screen: no screenshots or preview in the task switcher.
  • filterTouchesWhenObscured against overlay attacks (tapjacking).
  • Fields with IME_FLAG_NO_PERSONALIZED_LEARNING: the keyboard does not learn passwords.
  • Clipboard with EXTRA_IS_SENSITIVE (Android 13+) and wiped after 30 s.
  • Secrets as ByteArray in the Rust core, with zeroize on lock.
  • Configurable auto-lock, when the screen turns off and when the app goes to the background.
  • Failed attempts with exponential backoff; optional wiping after N attempts.
  • A warning, without locking, if the device is rooted or has an unlocked bootloader.
Known limitation

Compose and the JVM handle text as an immutable String, which cannot be wiped from memory at will. Mitigation: plaintext only exists while a field is shown or edited, the Rust core holds the keys and the decrypted data, and garbage collection is requested on lock. We should document it and not promise more than we can deliver.

5 · Backup

Backup without losing security

A backup does not weaken security if it meets two conditions: it leaves the phone already encrypted with keys only the user has, and the app does not need to connect to anything to make it.

That is why the app uploads nothing. It writes the encrypted file to a folder the user picks with the Android picker (Storage Access Framework). If that folder belongs to Nextcloud, Google Drive, Syncthing or an SD card, the provider's app is the one that syncs it. OpenPassword still has no network permission and the provider only sees an opaque blob.

The secret key is what makes it safe to keep the backup in the cloud. Even if someone steals the file and the master password is weak, without the 128 bits of the secret key brute force is not viable.

1 · Manual exportThe user taps «Exportar» and picks a destinationNoMinimalMVP
2 · Automatic backupWorkManager writes to the chosen folder daily and after changes; rotation of N backupsNoMinimalv1
3 · File-based syncSeveral devices read and write the same folder (Syncthing); per-item merge with vector clocksNoLow conflictsv2

.opvault format v1

An open, documented format, so it can be decrypted with a command-line tool even if the app disappears.

# plaintext header, authenticated as associated data
magic           "OPVAULT\x01"
header {
  format_version  1
  kdf             argon2id, m=262144, t=3, p=4
  salt            32 bytes
  secret_key_id   HKDF(SK)[0..4] # does not reveal bits of the SK
  wrapped_vk      XChaCha20-Poly1305(KEK, VK)
  wrapped_fk      XChaCha20-Poly1305(VK, FK)
  created_at      1793257200
}
# items encrypted in blocks; AAD = SHA-256(header)
body            STREAM-BE32(FK, items)
Recovery: what the user must be told on day one

With the master password and the emergency kit everything can be recovered on a new phone. If they lose both, nobody can recover the data, not even us. That is the price of security and setup must make it clear before continuing.

On-disk data model

-- No titles, types or URLs in the clear
vault (
  id            BLOB PRIMARY KEY,
  wrapped_vk    BLOB,   -- by KEK
  wrapped_vk_bio BLOB,  -- by Keystore
  kdf_params    BLOB,
  salt          BLOB
)
item (
  id            BLOB PRIMARY KEY,
  vault_id      BLOB,
  wrapped_ik    BLOB,
  overview      BLOB,   -- type, title, URL
  details       BLOB,   -- secret fields
  revision      INTEGER,
  deleted       INTEGER
)

On unlock only the overview blobs are decrypted for the list and search. The details are decrypted when an item is opened and discarded when it is closed.

7 · Roadmap

From the spec to 1.0

Phase 0 · 3–4 weeks · done

Foundations

Threat model, cryptographic and .opvault format specifications. op-core in Rust with vector tests and the decryption CLI. CI with reproducible builds and permission checks.

Phase 1 · 6–8 weeks · done

Android MVP

Setup with emergency kit, unlock, vault with the five basic types, search, generator, auto-lock, export and import. Closed beta.

Phase 2 · 6 weeks · done; F-Droid paused

Daily use

Autofill, TOTP, automatic backup, vault health, importers and the remaining types. F-Droid publication.

Phase 3 · preparation done; external audit pending

Audit and 1.0

External audit of the core and the app (for example, Cure53, Trail of Bits or through OSTIF), fixing findings and a responsible disclosure programme.

Phase 4 · pending

Beyond

File-based sync, passkeys, attachments, multiple vaults, and desktop and iOS apps reusing op-core.
